# Antigravity Task Brief — NER-LINK Phase 0 + Phase 1

Read `NER_LINK_MASTER_PRD.md` first. It is the source of truth for product intent, architecture, safety rules, team boundaries and phase acceptance criteria.

## Objective
Implement only repository setup and the foundation of the geographic data layer. Produce a reproducible local environment and a real, routable OpenStreetMap road graph for a configurable corridor. Do not implement the image ML pipeline, trained risk model, offline PWA, GPS streaming, or complete dashboard yet.

## Required outcomes

### A. Inspect before changing
1. Inspect the repository and report existing code, environment and test setup.
2. Run `git status`; preserve existing user changes.
3. Provide a short proposed file-level plan before making edits.

### B. Local infrastructure
1. Use Docker Compose for PostgreSQL with PostGIS, Redis, and FastAPI.
2. Keep secrets in `.env`; commit only `.env.example`.
3. Avoid PostgreSQL host port conflicts; use a configurable host port, defaulting to 55432 if available.
4. Add `/health/live` and `/health/ready`; readiness must check database connectivity and required PostGIS support. Redis status should be reported if the phase requires Redis.
5. Add useful logs and clear service startup instructions.

### C. Database and migrations
1. Configure SQLAlchemy and Alembic.
2. Create a reviewed initial schema for users/roles, districts, road nodes, road segments, road segment current state, incidents, incident evidence, vehicles, vehicle locations, deliveries, trips, route recommendations, weather observations, satellite candidates, risk predictions, alerts and audit logs. Tables not used yet may have only foundational fields; do not create fake application logic just to populate them.
3. Use appropriate PostGIS geometry types and spatial indexes.
4. Preserve stable road identifiers, OSM identity, direction/one-way/access fields, edge length and source/target nodes.
5. `safety_score` convention must be 0–100 with 100 safer; disruption probability is a separate 0–1 value. Confirmed blocked status is independent from model score.
6. Add foreign keys, constraints and indexes where appropriate.
7. Generate and inspect the first Alembic migration. Do not blindly trust autogenerated migrations.

### D. OpenStreetMap road graph import
1. The study area must be configurable. Use Guwahati–Tawang only as a provisional demo corridor; do not hard-code it.
2. Use an approach that preserves road topology and directionality. Suitable options include OSMnx/NetworkX for a bounded study area or a documented equivalent. Merely importing line geometries is not enough.
3. Persist canonical nodes and edges in PostGIS, including edge geometry, OSM identifiers, one-way/access rules, road class, length and a base travel-time estimate if available.
4. Keep stable internal edge IDs to be shared with frontend and ML.
5. Make imports repeatable and safe to rerun; document data freshness and OpenStreetMap attribution.
6. Validate a set of test origin/destination pairs and graph connectivity. Do not label imported roads `OPEN` merely because OSM includes them; initialize operational status as `UNKNOWN` until operational evidence is present.

### E. Minimal read-only API
Provide only the Phase 1 endpoints needed to verify the foundation, such as:
- `GET /api/v1/roads` with bounded/bbox filtering and pagination or equivalent limits.
- `GET /api/v1/roads/{id}`.
- A GeoJSON endpoint for road segments in a requested map bounds.
- A small graph validation/diagnostic command or script; do not expose a dangerous public debug endpoint in production mode.

The API must have response schemas, sensible error handling and tests. Never send the entire regional dataset to the browser as one unbounded response.

### F. Tests and acceptance criteria
Add and run tests that cover:
- Settings validation and missing environment configuration.
- `/health/live` and `/health/ready` behaviour.
- Database connection and PostGIS version/extension check.
- Alembic migration up from an empty database.
- Road/node/edge constraints and spatial query basics.
- OSM import idempotency or a documented safe reset/re-import procedure.
- Graph topology and one-way constraints for selected test paths.
- Correct GeoJSON feature IDs/geometries and bounded query results.
- Error paths when the database or import data is unavailable.

Do not fabricate successful command outputs. If Docker is unavailable, state that runtime tests could not be executed and provide the exact commands the developer must run.

## Engineering constraints
- Follow the master PRD's division of responsibilities: backend owns graph topology, stable IDs, coordinate snapping and route computation; frontend only renders geometry and sends selected coordinates.
- Keep PostgreSQL/PostGIS as persistent source of truth and Redis for server-side transient state/events. Offline device storage will be IndexedDB in a later phase, not Redis.
- Do not add MongoDB, Kafka, Kubernetes or another backend framework.
- Add docs for setup, import, reset, migrations, verification and common errors.
- Keep sample/test data clearly marked as synthetic; never mix it with operational observations without a source field.

## Agent completion response format
At completion, report:
1. Summary of what was implemented.
2. Files added/changed.
3. Architecture decisions and trade-offs.
4. Exact commands run and actual test results.
5. Manual commands for the developer to validate locally.
6. Known limitations and any blocker.
7. The next smallest recommended task (do not start Phase 2 automatically).
